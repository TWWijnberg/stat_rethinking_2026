03Surface the trade-off, never the limitation

Step 05 asked you to sign off on brms refusing to sample from a flat prior. That is a fact about a library. You are a statistician, not the maintainer of brms, so there was nothing for you to rule on.

Worse, the wall was avoidable. The whole prior predictive check is five lines of base R — draw the priors, push them through the linear predictor, add noise. It gives the same answer:

                  by hand     via brms
below 0 kg       2.1%        2.1%
above 15 kg      0.1%        0.1%
median          4.6 kg      4.5 kg
95%             [0, 9]      [0, 9]
Ruled

State the audience in CONTEXT.md: the human is a statistician who understands what a method implies, not an engineer who knows what a library cannot do. Then apply a two-tier rule.

Tier one — the tool cannot do it, but the method is still available. Route around it. Write the code by hand. Say nothing, or one line in the script comment. This is not a decision and it never reaches the decision list.

Tier two — the tool cannot do it, and that removes a method from the table. Now it is a decision, but present it as a trade-off in methodological terms: what the method would buy, what it costs in time or reliability, and what the fallback method is. Never present the error message.

The test is whether a method is lost. If nothing is lost, there is nothing to weigh. A07's M5 lost nothing, so it should never have been written.

Alternative

Same two tiers, but the agent also logs every tier-one workaround in a Constraints section of the README.

A later reader can see why a step has hand-written code instead of a library call. It is more bookkeeping, and most entries will never be read.

10Test the code first, mimic the data second

The first generative model copied group structure, integer group sizes and the real correlation matrix. None of it was needed, and one part of it did harm.

Ruled

The chain the step is testing, in one line: the synthetic data mirrors the causal structure; the statistical model applies the identification strategy for the chosen estimand, using the adjustment set the DAG gives; recovery asks whether that pairing returns the parameters we put in.

synthetic data      mirrors the DAG
statistical model   identification strategy + adjustment set
recovery            does that pairing return the true values?

What this cannot catch: a wrong DAG. If the assumed structure is wrong, the simulation is wrong the same way, so the adjustment set that follows from it recovers cleanly and tells you nothing. The error cancels. Recovery tests the identification strategy given the DAG; item 20 tests the DAG itself. Neither substitutes for the other, and A07 ran only the first.

Primary — the generative model exists to test whether the statistical model recovers the causal quantity. Three criteria.

Mirror the DAG. Every variable and every arrow the DAG asserts is in the simulation. This is what makes recovery a test of the causal claim and not of a regression.
Match the outcome's form. Whatever the statistical model assumes about how the outcome is produced — linear in its predictors, Gaussian noise — the generative model produces. Otherwise a recovery failure is ambiguous between a bug and misspecification.
Every true value recoverable in principle, the estimand included.

The generative model is deliberately richer than the statistical model, and the gap is the point. A07's simulation holds four variables and four arrows. The total-effect model holds one predictor. Group size exists in the simulated world and genuinely moves weight, and the fitted model does not mention it.

That omission is required, not sloppy: leaving group size out keeps the path F -> G -> W open, so its contribution lands in the food coefficient. That is what "total" means. Recovery then checks whether omitting the mediator really does return the total effect, on data where the answer is known.

Close the gap and there is nothing left to test. If the simulation were just W = a + bF + noise, fitting Ws ~ Fs would recover b and confirm only that brms can fit a one-predictor regression.

One world serves both analyses, and they have different right answers:

Ws ~ Fs         should return  -0.03   got  -0.038   total effect
Ws ~ Fs + Gs    should return  +0.60   got  +0.492   direct effect

Same simulated data, two statistical models, two targets, both hit. A generative model built to match one of them could not have served the other. So: structure richer, outcome's form identical.

Secondary — resemblance, only where it changes how the estimator behaves. Match the sample size, and match the features that drive the estimator's geometry. In A07 that was the 0.90 correlation between food and group size, which is what makes the direct effect imprecise. Nothing else. A variable that only ever appears as a predictor does not need a realistic distribution.

When they conflict, offer two datasets and let the human choose. One tuned for recovery: round invented values, effects clearly away from zero, so a broken estimator fails visibly. One tuned for resemblance: calibrated to the real data, so the fit is exercised in the regime it will actually meet. The cost is a second recovery run. That is a decision for the human, not a rule.

And a true value near zero is itself a decision to surface. If calibration drives a true effect to about zero, say so before the sign-off: the recovery test for that quantity is weak, because an estimator that always returned zero would pass it.

A07 is the worked example, and it went wrong my way. Calibrating the two weight coefficients to the real correlation matrix drove the true total effect to -0.03. I mentioned it as an aside inside another decision rather than surfacing it as its own. The direct effect at +0.60 kept the check honest by accident.

One correction on the record: my first version of this item said "same model, both directions". That is wrong, and it would have destroyed the point of the step.

Rejected

Give a checklist — marginals, correlations, grouping, discreteness — and make the agent rule each one in or out.

Nothing would be forgotten. Every analysis pays four more sign-offs, and it still would not say which goal wins.

11Be able to defend each prior, and the set of them

The intercept prior normal(0, 0.2) came from convention. In kilograms it claimed the average fox weight was known to within half a kilo. A07 also checked the priors one at a time, and only checked them as a set after you asked.

Ruled

Every prior needs two things.

A reason. Why this, and not something else. Naming the class — weakly informative, informative, empirical — says what kind of reason it is. "Empirical" is the admission that the reason came from this dataset.

A statement in real units. normal(0, 0.2) tells you nothing. "The average fox weighs between 4.07 and 4.99 kg" tells you it is far too confident. Same prior; only one version can be judged.

Then simulate data from the priors alone, and look at it. Three questions:

1  Could a fox weigh that?
2  Does a deliberately bad prior look different?
3  Do the priors leave room for the real data, and for the
   values used to build the synthetic data?

Question 2 is what lets the check fail. Without a bad prior to compare against, "looks fine" is unfalsifiable. Question 3 catches a failure the recovery step names but cannot see coming: if a true value sits far out in the tail of its own prior, recovery pulls toward zero and you blame the code.

Then after the fit, check whether the prior is still steering. Turn the prior up and down and watch how far the answer moves. Barely moves means the prior is not doing much; moves a lot means it is steering. This is power-scaling sensitivity — priorsense::powerscale_sensitivity(), which reads the existing draws and needs no refit. Above about 0.05 means the prior is doing real work.

It catches what a prior predictive check cannot. That one asks, before the data, whether the priors are sane. This one asks, after the data, whether the prior is still deciding the answer. A07's priors passed the first and failed the second:

direct effect model   b_Fs  prior 0.120  likelihood 0.139  prior-data conflict
total effect model    all variables 0.002 to 0.012  clean

refitting the direct model with wider slopes:
  normal(0, 0.5)  +0.566 kg   normal(0, 1)  +0.703 kg   normal(0, 2)  +0.753 kg

The mechanism is worth knowing: the direct-effect model has predictors correlated at 0.90, so each coefficient is weakly identified — and weak identification is exactly where a prior does the most work. My step 05 sign-off said "no sensitivity candidates remain". This diagnostic would have said otherwise.

One extra, only when there are many predictors. With one or two, the picture above shows everything. With ten or twenty, coefficients that each look harmless jointly claim the model explains nearly all the variation. Then check the implied R-squared.

same slope prior normal(0, 0.5)
k =  1   median R2 = 0.16
k = 20   median R2 = 0.92

A07 results, for reference: 2.1% of implied weights below 0 kg and 0.1% above 15 kg; the vague prior put 44% outside those bounds; the observed mean, sd, min and max all landed at the 52nd to 55th percentile of the prior predictive; and the true values used for the synthetic data sat at the 88th, 8th and 48th percentiles of their own priors.

Detail — for the skill file, not the decision

R-squared is a pushforward, not a comparison of datasets: for each prior draw, take the linear predictor at the observed predictor values, then var(mu) / (var(mu) + sigma^2). No outcome enters.

And do not correlate one outcome vector against another. cor(y_prior, y_synthetic) is about -0.002, and it stays at zero whether the slope prior has sd 0.05 or 5.00, because both vectors carry independent noise. A check that answers the same for a sane prior and an absurd one is not a check. The useful comparison between those two objects is coverage, which is question 3.

21Name the middle link with the standard term

Step 01 produces a sentence in kilograms. The DAG step produces an adjustment set. Nothing in the skill names the object in between — the observable quantity the model actually estimates. A07 called it an "identification strategy", which is borrowed from the wrong literature.

Ruled

Adopt the decomposition from Lundberg, Johnson & Stewart (2021), which is the standard citation for exactly this gap.

theoretical estimand   the target quantity, tied to the question
empirical estimand     the observable quantity informative about it,
                       under stated identification assumptions
estimation strategy    what is actually done with the data

Keep two DAG-side terms beside them: identification assumptions (the DAG itself, plus no unmeasured confounding) and adjustment set (what follows from them, by the backdoor criterion).

Put "identification strategy" on the avoid list, with the reason. In econometrics it names a research design — instrumental variables, difference-in-differences, regression discontinuity. Someone reading "our identification strategy is to condition on group size" expects a design and finds a covariate.

The gain is concrete. A07's empirical estimand was the coefficient on standardised food in a regression of standardised weight on food alone. That is the object recovery checks, and until now the skill had no word for it.

Rejected

Keep one word, estimand, and rely on the adjustment set to imply the rest.

Fewer terms to learn, and CONTEXT.md stays short. But the thing recovery tests still has no name, which is how A07 ended up inventing one.

The one real gap is the DAG step, and it has been measured rather than estimated. pgmpy finds adjustment sets well, but its get_independencies() attempts the full exponential enumeration, has an open issue against it, and failed all nine textbook questions dagitty solved.

The fix is to not use it. The local Markov property gives one independence statement per node — linear, not exponential — and networkx supplies descendants, parents and is_d_separator directly. Limits worth knowing: minimal separators are brute force over subsets, so a DAG past about ten nodes would need Takata's algorithm as dagitty uses. No latent variables or bidirected edges. Continuous data only. None of that binds for homework DAGs. The prototype is at docs/dag_tools_prototype.py.
